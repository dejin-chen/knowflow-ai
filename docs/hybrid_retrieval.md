# BM25 + RRF 混合召回

## 1. 召回问题与目标

结构化 LLM Rerank 只能重新排列已经进入候选集的 Chunk。如果正确证据没有被
Chroma 找到，Reranker 再聪明也无法凭空补回证据。

纯向量召回擅长理解近义表达，但面对错误码、金额、制度名称、服务台名称和精确短语时，
字面匹配有时更可靠。因此当前链路增加第二条 BM25 关键词召回通道，再通过 RRF 合并两路排名：

```text
用户问题
├─ 生成 Embedding → Chroma 向量候选 ─┐
└─ 轻量分词 → SQLite Chunk → BM25 候选 ─┤
                                      ↓
                              加权 RRF 融合
                                      ↓
                              最多 12 个候选
                                      ↓
                              结构化 LLM Rerank
                                      ↓
                                 最终 Top-K
```

这里有三个不同目标：

- 向量召回负责寻找“意思相近”的文本；
- BM25 负责寻找“字面词项相同”的文本；
- RRF 负责统一两种不同检索器的排名，不负责理解正文。

## 2. BM25 是什么

BM25 是经典关键词检索算法。可以先把它理解为一个更合理的“关键词计分器”：

- 查询词出现在某个 Chunk 中，该 Chunk 得分增加；
- 越少见的词通常越有区分度，权重越大；
- 会考虑 Chunk 长度，避免长文本仅凭出现词多就一直占优；
- 同一个词重复很多次后，收益会逐渐变小。

项目使用 `rank-bm25` 的 `BM25Okapi`，没有手写核心公式。这样既使用经过验证的实现，
又把精力放在中文分词、数据流、融合策略和评估上。

## 3. 中文为什么需要先分词

英文句子天然有空格，中文没有。直接按空格切分时，一整句中文可能被视为一个词，BM25
几乎无法匹配。`RetrievalTokenizer` 使用轻量规则：

- 英文、数字保留完整词元，例如 `VPN`、`403`；
- 中文连续文本切成双字片段，例如“培训费用”得到“培训、训费、费用”；
- 数字中的千分位逗号会移除，使 `20,000` 与 `20000` 能匹配；
- BM25 与词法降级 Reranker 共用同一个分词器，避免两套规则行为不一致。

这不是专业中文分词的完全替代，但依赖小、结果稳定，适合当前知识库规模。文档量和词汇复杂度
上升后，可以比较 jieba、模型分词、PostgreSQL 全文检索或 OpenSearch。

## 4. 为什么使用 RRF

Chroma 返回的是向量距离，数值越小越相似；BM25 返回的是词法得分，数值越大越相关。
两个分数的量纲和范围完全不同，不能直接相加。

RRF（Reciprocal Rank Fusion，倒数排名融合）只使用名次：

```text
RRF(chunk) = 向量权重 / (k + 向量排名)
           + BM25 权重 / (k + BM25 排名)
```

一个 Chunk 同时被两路检索器排在前面时，会得到更高融合分；只被其中一路找到时也能保留。
本项目在 30 题开发集上固定以下参数：

- `k = 60`
- 向量权重 `1.0`
- BM25 权重 `1.5`
- 两路最多各取 `12` 个候选

权重不是“BM25 准确率高 50%”，只表示当前融合公式中更重视 BM25 的排名贡献。

## 5. 为什么没有再建一个 BM25 数据库

当前版本每次检索都从 SQLite 读取当前知识库的 `document_chunks`，临时构建 BM25 语料。
这样做有两个现实原因：

1. SQLite 中的 Chunk 正文仍是主数据，不需要维护第四套持久化索引；
2. 文档重切分或删除后，BM25 下一次查询自然读取新数据，不会产生旧关键词索引。

代价是每次查询都要扫描该知识库 Chunk，时间和内存开销随文档量增长。因此当前实现适合中小规模
知识库和受控内部工作负载，不应描述为海量文档方案。规模扩大后可将这一服务替换为 PostgreSQL
全文检索、Elasticsearch 或 OpenSearch，上层 `RetrievedChunk` 合同和 RRF 流程可以保留。

## 7. 检索结果如何溯源

BM25 和 Chroma 最终都只需要给出 `chunk_id`。RRF 合并 ID 后，
`SemanticSearchService` 一次性回查 SQLite，得到 Chunk 正文、`document_id`、
`knowledge_base_id` 和文件名。

因此：

- 正文不会和 `document_id` 一起向量化；
- Chroma、BM25 和 RRF 都是“找到候选 ID”的手段；
- SQLite 仍是最终正文与业务关系的主数据；
- 更换检索器不会推倒文档、会话和引用表。

BM25-only 候选没有 Chroma 距离，所以其 `distance` 和 `vector_rank` 为 `null`，但仍有
`bm25_rank`、`bm25_score`、`fusion_rank` 和 `fusion_score`。

## 8. 资料不足与缓存为什么也要修改

加入 BM25 后，正确证据可能只有词法命中而没有向量距离。如果仍要求“必须存在合格 distance”，
系统会错误拒绝 BM25-only 证据；但任意正 BM25 分数也不能直接视为充分证据，因为常见词轻微重合
同样会得到正分。

因此“候选最低分”和“回答证据阈值”被拆开：正分结果可以进入候选，只有 BM25 score 达到
`8.0` 才能单独绕过向量距离拒答。当前知识库中，3 道确实依赖 BM25 补回且向量距离超阈值的问题，
正确证据分数均超过 `15`；8 道人工构造无答案问题的最高分位于 `1.48～4.86`。这仍是当前语料上的
启发式阈值，后续需要正式无答案集继续评估拒答 Precision、Recall 和 F1。

回答缓存键也加入 BM25 开关、Top-K、候选最低分、证据阈值和 RRF 权重。检索策略改变后，同一个问题会生成新键，
不会复用旧检索配置下的答案。

## 9. 评测方法

先使用 30 题开发集选择权重，再锁定参数运行 100 题独立测试集。100 题没有用于调参。
每道题使用同一问题、同一 Embedding 和同一知识库，对比三条链路：

1. 纯 Chroma 向量召回；
2. 向量 + BM25 + RRF；
3. 向量 + BM25 + RRF + LLM Rerank。

标注使用预期文件名和关键事实词，不绑定重切分后可能变化的 Chunk ID。

### 30 题开发集

| 指标 | 纯向量 | 等权 RRF | 固定权重 RRF |
| --- | ---: | ---: | ---: |
| 候选命中率 | 96.67% | 100% | 100% |
| HitRate@3 | 80.00% | 93.33% | 96.67% |
| MRR | 0.6167 | 0.8333 | 0.8778 |

固定权重是向量 `1.0`、BM25 `1.5`。没有为了最后一道开发题继续调参，避免过拟合。

### 100 题独立测试集

| 指标 | 纯向量 | 混合 RRF | 混合 RRF + LLM Rerank |
| --- | ---: | ---: | ---: |
| 候选命中率 | 95% | 100% | 100% |
| HitRate@3 | 82% | 93% | 100% |
| MRR | 0.56 | 0.8483 | 1.00 |
| 关键词召回率 | 0.8008 | 0.93 | 1.00 |

与“纯向量候选 + LLM Rerank”的历史基线 `94%` 相比，完整混合检索排序链路的
HitRate@3 增加 `6` 个百分点。混合召回补回了 5 道纯向量候选完全遗漏的问题。

### LLM Rerank 成本

| 指标 | 结果 |
| --- | ---: |
| 调用次数 | 100 |
| 降级次数 | 0 |
| 平均 Token | 3401.75 |
| 总 Token | 340175 |
| 平均延迟 | 3191.50 ms |
| P95 延迟 | 4687.71 ms |

`100%` 只表示当前固定知识库和人工标注测试集上的检索排序结果，不等于线上回答准确率，
也不代表未来所有文档都能达到 100%。完整原始报告保存在
`evaluation/reports/hybrid_retrieval_comparison_2026-08-03.json`。

## 10. 实现总结

- 召回和重排是两个不同阶段，Rerank 不能修复候选缺失；
- BM25 与 Embedding 分别覆盖词法和语义检索需求；
- 不同检索器原始分数不能直接相加，RRF 用排名完成融合；
- 新检索通道会影响资料判断、缓存键、API 字段和评测，不能只改一个搜索函数；
- 开发集用于调参，独立测试集用于最后验证；
- 指标提升必须同时报告样本量、成本、延迟和适用边界。

## 11. 实现结果

> 实现基于中文双字分词的 BM25 与 Chroma 双路召回，使用加权 RRF 融合不同量纲的检索结果，
> 再通过带 chunk_id 白名单的结构化 LLM Rerank 生成最终 Top-K；在 100 条人工标注独立测试集上，
> 候选命中率由 95% 提升至 100%，HitRate@3 由纯向量的 82% 提升至 100%，MRR 由 0.56
> 提升至 1.00，并记录平均 3402 Token、3.19 秒延迟和 0 次降级。

## 12. 关键设计决策

- Chroma distance 与 BM25 score 的方向和量纲不同，直接相加会产生不可解释的排序偏差；RRF 只使用名次融合。
- RRF 的 `k` 控制头部名次差异的平滑程度，两路权重控制语义召回与关键词召回的相对贡献。
- 当前语料规模允许按请求动态构建 BM25，减少独立索引的一致性成本；规模扩大后应迁移到持久化倒排索引。
- BM25-only 候选必须通过高置信词法门槛，不能用缺失的 distance 绕过证据不足判断。
- 开发集用于选择参数，独立测试集用于估计泛化效果，避免把调参收益误当成最终质量。
- 固定测试集的 100% 只说明该样本集全部命中，不代表未知线上分布的准确率。
- 检索通道通过统一 `RetrievedChunk` 合同接入，上层 RAG 不依赖 BM25 的具体索引实现。
