# 工程基础与项目结构

## 建设目标

工程基础的目标是建立可维护的 Python AI 应用骨架，避免业务能力耦合在单文件原型中。

一个可维护的 RAG 平台不仅要能回答问题，还必须具备清晰的工程边界：

- API 如何组织
- 配置如何管理
- 数据库如何连接
- 日志如何统一
- 测试如何编写

## 实现范围

- 创建 FastAPI 后端项目结构
- 创建 Streamlit 前端目录
- 配置 `.env.example`
- 配置统一日志
- 配置 SQLite + SQLAlchemy
- 实现健康检查接口
- 编写 pytest 测试

## 为什么这样拆目录

`api` 只负责 HTTP 请求和响应，不直接写复杂业务。

`services` 放业务流程，例如后续的文档解析、文本切分、RAG 问答和 Agent Router。

`repositories` 负责数据库读写，避免业务逻辑和 SQL 操作混在一起。

`models` 放数据库表结构，`schemas` 放接口请求和响应结构。

这种拆分能让项目从一开始就具备扩展性。后续新增文档管理、向量索引、问答日志时，不需要推倒重来。

## 健康检查接口

健康检查接口是部署时最常见的基础接口。

路径：

```text
GET /api/health
```

它用于判断服务是否正常启动。以后使用 Docker、云服务器或反向代理时，都可以通过这个接口做存活检查。

## 实现总结

- FastAPI 应用如何组织成正式项目结构
- `.env` 如何承载不同环境的配置
- SQLAlchemy 的 engine 和 session 分别负责什么
- pytest 如何测试接口返回结果
- 为什么生产工程要重视分层、配置和可观测性，而不只是跑通最小链路

## 实现结果

交付结果：

KnowFlow AI 的后端骨架基于 FastAPI、SQLAlchemy 与 SQLite，包含配置管理、统一日志、数据库连接、健康检查和 pytest 测试，为文档管理、向量检索与 RAG 问答提供可扩展基础。

## 关键设计决策

1. 为什么不采用单文件架构？

决策说明：正式项目需要清晰分层，否则知识库、文档、检索、问答和日志会相互耦合，增加测试、维护和扩展成本。

2. 为什么先用 SQLite？

决策说明：SQLite 适合当前单机部署边界，运维成本低；通过 SQLAlchemy 隔离数据访问后，可较平滑地迁移到 PostgreSQL。

3. 健康检查接口有什么用？

决策说明：健康检查使部署平台、Docker 编排和运维脚本能够判断服务状态，是后端服务的基础可观测入口。
